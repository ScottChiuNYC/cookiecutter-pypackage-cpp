# Project Skeleton Contract

Contract version: 1.0

## 1. Purpose

This document is the normative development contract for the reusable C++/Python project skeleton generated by `cookiecutter-pypackage-cpp`.

It tells developers and AI agents **where implementation belongs and how it connects to the existing build, packaging, dependency, binding, test, and CI machinery**. It is intentionally domain-agnostic. A domain implementation specification such as `essence.md` should describe what must be implemented; this document describes how that implementation is placed into this repository skeleton.

A developer working from a domain specification should read this contract before adding source files, dependencies, bindings, tests, or build-system changes.

If a generated project intentionally evolves away from this skeleton, update its copy of this contract in the same change that alters the skeleton convention. The project-local copy is authoritative for that project.

## 2. Ownership boundary

The project skeleton owns:

- repository layout and source locations;
- C++ and Python build integration;
- pybind11 extension placement;
- dependency declaration and wiring;
- packaging and wheel construction;
- C++ and Python test integration;
- build presets and supported developer build flows;
- CI entry points.

A domain implementation specification owns:

- logical components and public behavior;
- domain APIs and data contracts;
- algorithms and numerical methods;
- supported and unsupported product/model scope;
- domain validation and acceptance criteria;
- which third-party capabilities are required.

The domain specification may require a library such as Tasmanian or Eigen, but the dependency is added and wired according to this skeleton contract. It should not redefine repository paths, package layout, or build mechanics unless the skeleton itself is intentionally being changed.

## 3. Repository layout

The standard generated layout is:

```text
project root
├── CMakeLists.txt
├── CMakePresets.json
├── build.py
├── pyproject.toml
├── vcpkg.json
├── vcpkg-configuration.json
├── cpp/
│   ├── CMakeLists.txt
│   ├── include/
│   │   └── <module>_core/
│   ├── src/
│   └── bindings/
├── src/
│   └── <module>/
├── tests/
│   ├── cpp/
│   └── python/
├── examples/
│   └── cpp/
└── docs/
    └── development/
```

Here `<module>` means the Python module name chosen when the project was generated.

### 3.1 C++ public headers

Public C++ headers belong under:

```text
cpp/include/<module>_core/
```

Headers intended to be consumed by another C++ target or by bindings should live under this public include root rather than beside implementation files.

### 3.2 C++ implementation

Production C++ implementation files belong under:

```text
cpp/src/
```

The generated `cpp/CMakeLists.txt` currently discovers top-level `cpp/src/*.cpp` files. If the project introduces nested source directories or a different target decomposition, update `cpp/CMakeLists.txt` explicitly so the build graph matches the new structure. Do not assume nested files are discovered automatically.

### 3.3 Python bindings

pybind11 binding translation units belong under:

```text
cpp/bindings/
```

The generated skeleton starts with one binding source. If bindings are split across multiple translation units, update `cpp/CMakeLists.txt` so every required binding source is compiled into the extension module.

Binding code should adapt the C++ public interface to Python. Domain algorithms should remain in the C++ implementation or Python domain layer rather than being duplicated inside binding glue.

### 3.4 Python package

Pure Python implementation, package exports, type helpers, calibration/research code, and Python-facing orchestration belong under:

```text
src/<module>/
```

The compiled extension is emitted directly into this package directory by CMake so development tests and built wheels use the same package namespace.

Keep the package import surface intentional. When new native APIs are exposed, update Python exports and type information where appropriate.

### 3.5 Tests

C++ GoogleTest sources belong under:

```text
tests/cpp/
```

Python pytest sources belong under:

```text
tests/python/
```

The generated C++ test CMake file discovers top-level `tests/cpp/*.cpp`. If tests are reorganized into nested directories or multiple executables, update `tests/cpp/CMakeLists.txt` explicitly.

Tests required by a domain specification are domain-owned acceptance criteria; their physical location and registration follow this skeleton contract.

### 3.6 Examples

Standalone C++ examples belong under:

```text
examples/cpp/
```

Examples are not substitutes for tests. If an example requires build integration, register it through the existing examples CMake layer.

## 4. CMake target and dependency direction

The root `CMakeLists.txt` establishes the project language standard, enables CTest, and delegates to the C++ implementation, examples, and tests.

The generated C++ layer provides:

- a static C++ core library built from `cpp/src/`;
- public include access through `cpp/include/`;
- a pybind11 extension linked to the C++ core library;
- direct placement of the extension in `src/<module>/`.

When expanding the project, prefer explicit target-based CMake usage:

- attach include directories with `target_include_directories`;
- attach dependencies with `target_link_libraries`;
- attach compile definitions/options to the target that owns them;
- preserve dependency direction from reusable core code toward adapters/bindings, not the reverse.

Do not place domain logic in root build files merely because it is convenient.

## 5. Adding C++ dependencies

vcpkg is the standard package manager for C++ dependencies.

For a normal new C++ dependency:

1. add the dependency to `vcpkg.json`;
2. configure it in `vcpkg-configuration.json` or `vcpkg-ports/` only when registry/overlay behavior actually requires it;
3. use the package's CMake config from the appropriate project CMake file, normally with `find_package(... CONFIG REQUIRED)`;
4. link the imported target to the narrowest CMake target that needs it;
5. build and test on the supported platforms.

Do not change the recorded vcpkg baseline merely to add a normal dependency. A baseline change is a toolchain/dependency-set migration and should be treated as such.

The skeleton currently manages pybind11 through CMake `FetchContent`. Do not silently introduce a second pybind11 installation path. Moving pybind11 to vcpkg or another provider is a skeleton-level migration and must update this contract and the build consistently.

Overlay ports under `vcpkg-ports/` are reserved for dependencies that intentionally require repository-local port behavior. Do not create an overlay port when the standard vcpkg port is sufficient.

## 6. Adding Python dependencies

Python runtime dependencies belong in:

```toml
[tool.poetry.dependencies]
```

Development-only dependencies belong in the appropriate Poetry development group, currently:

```toml
[tool.poetry.group.dev.dependencies]
```

Keep runtime and development dependencies separate. If dependency changes affect the package build or test environment, validate both normal development installation and wheel construction.

## 7. Packaging contract

Poetry is the Python packaging frontend and `poetry.core.masonry.api` is the build backend.

`pyproject.toml` invokes:

```text
build.py
```

through `[tool.poetry.build]`. `build.py` selects the platform CMake configure/build presets and builds the native extension before Poetry finishes packaging.

The CMake build emits the extension directly into:

```text
src/<module>/
```

The wheel include rules package the resulting `.pyd` or `.so` beside the Python sources.

C++ sources required to build an sdist must also be covered by the `pyproject.toml` sdist include rules. If source/header/binding layout is expanded beyond the existing patterns, update those include rules in the same change. A source layout that works only from a Git checkout but cannot build from the sdist violates this contract.

A packaging change is complete only when a clean build artifact can import the package without relying on accidental files from the source tree.

## 8. Canonical build and test flows

Set `VCPKG_ROOT` to the intended vcpkg checkout before configuring.

### Windows

```powershell
cmake --preset windows-vcpkg
cmake --build --preset windows-release
ctest --preset windows-release-tests
$env:PYTHONPATH = "$PWD/src"
poetry run pytest tests/python
```

### Linux

```bash
cmake --preset linux-vcpkg-release
cmake --build --preset linux-release
ctest --preset linux-release-tests
PYTHONPATH="$PWD/src" poetry run pytest tests/python
```

For package validation, `poetry build` must continue to invoke the native build through `build.py`.

Project-specific helper scripts may wrap these commands, but the underlying CMake/Poetry build remains authoritative.

## 9. CMake presets

`CMakePresets.json` is the canonical location for supported configure, build, and test presets.

When a new platform, toolchain, or build mode is added, extend the presets rather than creating an unrelated parallel build path. `build.py`, documentation, local developer workflows, and CI should agree on preset names and semantics.

Environment-specific absolute paths should not be committed into shared presets unless they are intentionally part of the project contract.

## 10. CI contract

The generated `.github/workflows/build-and-test.yml` is the baseline continuous-integration entry point. It validates the release build, CTest, and pytest on the supported Windows and Linux configurations when implementation, dependency, build-system, or test files change.

Domain specifications define what correctness tests are required. CI defines how those tests are exercised automatically.

When implementation requires new validation, add the test to the appropriate C++ or Python test suite first; avoid embedding substantive domain tests directly in workflow YAML.

A change to build, dependency, packaging, or CI machinery must be validated through the narrowest relevant local/test path and then through the repository's normal PR checks.

## 11. Interface with domain implementation specifications

A domain implementation document should use logical requirements, for example:

```text
Required implementation units:
- discount curve
- swaption product
- SABR--Cheyette model
- pricing engine
- Python calibration layer
- Python bindings for the public pricing API
- C++ and Python acceptance tests
- Tasmanian as a required C++ dependency
```

The implementation agent maps those requirements through this contract:

```text
C++ public interface
-> cpp/include/<module>_core/

C++ implementation
-> cpp/src/

Python binding glue
-> cpp/bindings/

Python implementation
-> src/<module>/

C++ tests
-> tests/cpp/

Python tests
-> tests/python/

C++ dependency
-> vcpkg.json + target-level CMake wiring

Python dependency
-> pyproject.toml
```

The domain specification should not need to repeat these physical paths or build instructions.

## 12. Change discipline

Treat the skeleton as shared infrastructure.

A normal domain implementation may add source, bindings, dependencies, and tests using the extension points above. It should not redesign the build or package architecture incidentally.

If a task genuinely requires changing a skeleton convention, make the infrastructure change explicit and update all affected pieces together:

- this contract;
- build/package files;
- README or onboarding references;
- CI where applicable;
- generated-template source if the change should apply to future projects.

Do not allow the executable skeleton and this written contract to drift apart.

## 13. Developer/agent checklist

Before implementing a domain feature:

- read this contract and the domain implementation specification;
- identify which required components are C++, bindings, Python, tests, or dependencies;
- place each component in the skeleton-owned location;
- wire dependencies through the existing package/build mechanisms;
- update sdist/wheel rules if new source locations require it;
- run the relevant C++ and Python tests;
- validate packaging when bindings or package structure change;
- keep infrastructure decisions out of the domain specification unless the infrastructure itself is changing.

The intended reconstruction rule is:

> **Project Skeleton Contract + domain implementation specification + referenced mathematical/domain specifications should be sufficient for a fresh developer or AI agent to implement the in-scope functionality without inventing repository-layout, build, dependency, packaging, or test conventions.**
